# Follow-up — the CLV metric is mislabeled, and where the home skew really comes from

Generated by `scripts/clv_and_skew_diagnostics.py` (report-only), 2026-08-06,
`model_version=b9133b95d2ec`. 222 rated+resolved bets, 154 of them with closing odds.

## 1. The `clv` field is NOT closing line value — and it points the wrong way

`Main/app.py:1306`:

```python
entry["clv"] = round(model_prob - closing_impl, 4)
```

That subtracts the closing line's implied probability from **the model's own
probability**. It never compares two prices, so it is not closing line value — it is the
model's edge re-measured against a later line. It is large exactly when the model is
confident, which is precisely the quantity Phase 3 showed to be unreliable.

True CLV compares the price you got against the closing price:
`clv = closing_implied − bet_implied` for the side you took. Positive means the market
moved toward your team after you bet, i.e. you got a better number than the close.

```
n = 154 bets that have closing odds

  STORED 'clv'  (model_prob - closing_implied) : +4.67%   <- what the page reports
  TRUE   CLV    (closing_implied - bet_implied): -0.52%
      t=-0.54  p=0.593  95% CI [-2.42%, +1.38%]
      -> INDISTINGUISHABLE FROM ZERO
      beat the close on 50.6% of bets (coin flip = 50%)
```

**The model does not beat the closing line.** True CLV is −0.52%, statistically
indistinguishable from zero, and the market moved our way on 50.6% of bets — a coin
flip. The reported "+4.29%/+4.67% CLV" is the model's average self-assessed edge, not
evidence of skill.

The two metrics correlate with winning in **opposite directions**, which settles which
one is real:

```
  TRUE CLV   +0.1880   (positive = real skill signal)
  stored clv -0.1631   (negative = it is measuring overconfidence)
```

True CLV behaves the way the literature says a genuine skill metric should — bets that
beat the close win more often. The stored field behaves like the overconfidence measure
it actually is: the more edge the model claims, the *worse* the bet does.

**This is a real bug worth fixing on its own**, independent of any model work: the page
is currently reporting a number that reads as "we beat the market by 4.3%" when the
honest figure is "we match the market."

## 2. The home skew is real, but the `_HOME_PRIOR` blend is NOT the cause

Phase 2 attributed the home skew to the `_HOME_PRIOR = 0.53` blend. **That was wrong,
and this corrects it.**

```
  b) Is the _HOME_PRIOR=0.53 blend the cause?  NO
     mean RAW ensemble prob   : 0.5432
     mean BLENDED (live) prob : 0.5427
     blend shifts the mean by : -0.053pp -> it REDUCES the lean slightly
```

The blend pulls toward 0.53, which is *below* the model's own mean of 0.5432 — so it
slightly **reduces** home lean. The lean is in the model itself.

Nor is the overconfidence home-specific — it is symmetric across both sides:

```
     picked HOME: n=192  claimed 58.9%  actual 57.3%  gap +1.6pp
     picked AWAY: n= 91  claimed 55.5%  actual 53.8%  gap +1.6pp
```

The actual mechanism is that the model is **more home-leaning than the market**, and the
market is closer to the truth:

```
     mean MODEL  home prob : 0.5483
     mean MARKET home prob : 0.5346
     actual home win rate  : 0.5315   <- market is closer to truth
     model is +1.37pp more home-leaning than the market
     paired t-test: t=+2.23 p=0.0266 -> SIGNIFICANT
```

This is one of the few statistically significant findings in the whole investigation
(p = 0.027). A systematic +1.37pp excess home lean inflates home-side edge on essentially
every game, which pushes home games over the 0.05 threshold about twice as often as away
games (64 vs 30 value bets) — a bias, not a signal. Note the model's absolute home bias
vs *reality* is small (+0.56pp, n.s.); it is the bias **relative to the market**, which is
what edge is computed against, that matters.

## 3. Re-binning cannot rescue this — the sample is far too small

```
  edge 0.02-0.04   n= 30  20-10   66.7% [48.8,80.8]  ROI  +15.6%
  edge 0.04-0.06   n= 30  15-15   50.0% [33.2,66.8]  ROI   -8.0%
  edge 0.06-0.08   n= 22  16-6    72.7% [51.8,86.8]  ROI  +37.2%
  edge 0.08-0.10   n= 19  11-8    57.9% [36.3,76.9]  ROI  +11.4%
  edge 0.10-0.14   n= 19  8-11    42.1% [23.1,63.7]  ROI  -21.9%
  edge 0.14-1.00   n= 20  11-9    55.0% [34.2,74.2]  ROI  +16.2%
```

The sawtooth (66% → 50% → 73% → 58% → 42% → 55%) with **every confidence interval
overlapping every other** is the signature of noise. Any bin boundary drawn here will
find a "profitable segment" that is an artifact of where the lines were drawn.

No threshold beats simply taking every positive-edge game:

```
  edge >= 0.00   n=154  90-64  58.4% [50.5,65.9]  ROI  +8.7%
  edge >= 0.05   n= 95  54-41  56.8% [46.8,66.3]  ROI  +9.8%
  edge >= 0.10   n= 39  19-20  48.7% [33.9,63.8]  ROI  -2.4%
```

The one structural (non-noise) finding is the home/away asymmetry in *price*, not win
rate:

```
  all AWAY picks   n= 64  37-27  57.8% [45.6,69.1]  ROI  +9.3%
  all HOME picks   n=158  91-67  57.6% [49.8,65.0]  ROI  +0.9%
```

Nearly identical win rates, an order-of-magnitude difference in ROI — because away picks
are priced as underdogs, so the same win rate pays far more. This is a property of the
price structure and does not depend on a small-sample win-rate estimate.

## 4. Sample-size reality check

```
  Detecting a WIN-RATE difference between two buckets (80% power, alpha=0.05):
     10.0pp difference -> ~  400 bets PER BUCKET (  800 total)
      7.0pp difference -> ~  816 bets PER BUCKET ( 1633 total)
      5.0pp difference -> ~ 1600 bets PER BUCKET ( 3200 total)
     You currently have 20-70 per bucket.

  Information per observation:
     sd of one win/loss (0/1) : 0.500
     sd of one true CLV       : 0.120
     -> one CLV reading is worth ~17 win/loss readings.
```

At ~14 bets/day, 800 bets is ~2 months and 3,200 is most of a season. **Win rate is
simply too noisy a yardstick to tune anything on at this sample size.** True CLV carries
~17x the information per bet and is measurable the same evening rather than waiting on
outcomes — it is the right optimization target for iterating on the model.

## Recommendations, in order

1. **Fix the CLV metric** (`Main/app.py:1306`) — rename the current field to something
   honest like `edge_vs_close`, and add real CLV. Small, self-contained, and it stops the
   page reporting market-beating skill the data does not support. Highest value per unit
   of risk.
2. **Switch the evaluation target to true CLV.** Judge model changes by whether they
   improve CLV, not win rate. ~17x more information per bet and same-day feedback.
3. **Investigate the +1.37pp home lean relative to market** (p = 0.027) — the most
   statistically solid defect found. Likely a feature-level issue (home-field advantage
   double-counted, or park/travel features overweighted). Fixing it should reduce
   spurious home value-bet flagging directly.
4. **Do not re-bin edge to hunt for a profitable band.** Any band that looks good at
   n≈20-30 is noise. If you want a volume knob today, the away-side ROI asymmetry is
   the only structurally-grounded one — and even that deserves more data.
5. **Still open, still the deepest issue:** the model does not demonstrably beat the
   market (AUC 0.598 vs 0.594; true CLV ≈ 0). Until that changes, no threshold, bin, or
   calibration scheme will produce reliable profit.
